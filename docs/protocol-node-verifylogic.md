### 通信机制与基础规则

1. **双向回传机制**：节点间通信（如 A -> B），发送方 A 和接收方 B 均需向协议节点回传消息。
2. **时序规则**：A 在发送给 B 之前，先向协议节点发送回传，协议节点返回确认收到后，再向 B 发送消息。在协议节点的同一组验证中，先到的是**回传1**，后到的是**回传2**。
3. **双重签名机制**：
   - **内容签名**：由发送者签名（用于比对和判断接收者内容是否被篡改）。
   - **身份签名**：由各自节点签名（用于确保 `did` 为真）。
4. **消息数据结构**：每条回传的外层包含 `node_did`（本次发送者）及对应的身份签名；recorded_hop内层包含内容签名。
5. **单恶节点假设与可信名单**：
   - 假定链路中只有一个恶意节点，错误必从某次验证开始，此前存在绝对可信链路。
   - 协议节点始终维护一个已验证过的的 `did` 名单称作**可信名单**。
   - 本组验证中，回传1的身份必须在可信名单中。
   - **特殊情况**：若可信名单为空（Session 初始状态），则默认消息中的node_did在名单中。
6. 协议节点收到消息向发送者发送已收到后,便储存本次回传消息.

### 恶意节点判定机制

#### 1. 基础验证
先对每条回传消息进行格式层面的基本验证，确认无误后进入逻辑校验。

#### 2. 双回传场景（存在回传1与回传2）
存在一个发送者一个接收者。

**2.1 身份判断**
*   **若存在身份签名无法解开的情况：**
    *   **回传1解不开**：恶意节点必然在可信名单中,一起通报。
    *   **回传1解得开，但 DID 不在可信名单中**：恶意节点必然在可信名单中,一起通报。
    *   **回传1正解，回传2解不开**：回传2是恶意接收者（故意不签名或伪造签名）。
        *   **处理**：直接提取发送者（回传1）Payload 中的 `target_did`，将其判定为恶意节点。
*   **若两条回传消息身份签名均能正解：**
    *   **两个 DID 相同**：为同一节点发送，该节点必为恶意节点。
    *   **两个 DID 不同**（进入内容签名比对环节）：
        *   **回传1的 DID 不能解开自身的内容签名**：发送者（回传1）为恶意节点。
        *   **回传1的 DID 能解开自身的内容签名**，则继续比对回传2：
            *   **回传1的 DID 能解开回传2的内容签名**：
                *   **两条回传的内容签名相同**：回传2确为接收节点身份，进入后续的【内容及规则检测】。
                *   **两条回传的内容签名不同**（发送方双签/栽赃）：两条回传的内容签名均在发送方公钥下有效，却互不相同。按协议时序发送方应只签名一次、两条回传共享同一签名；签名不同说明发送方分别向协议节点与接收方各签署了一份不同内容。仅发送方私钥持有者可做到（密钥不可破假设），故判定**发送方为恶意节点**。
            *   **回传1的 DID 不能解开回传2的内容签名**（无有效接收者）：
                *   *可能性1*：恶意发送方将虚假内容签名发给了接收方（回传1恶）。
                *   *可能性2*：恶意接收方故意篡改内容签名导致解密失败（回传2恶）。
                *   **处理**：由于系统无法单方面分辨，将回传1与回传2**一起通报**。

**2.2 内容及规则检测（保持现有逻辑，代码位置可能变更）**
*   身份确定后，进行内容篡改和栽赃判断。直接使用当前项目中已有的verify_back_propagation。
*   确认内容没篡改和栽赃后，对具体内容进行判断：
    1、节点类型的逻辑判断。
    2、`hop_count` 变化判断。

#### 3. 单回传场景（仅存在一条回传消息）
恶意节点行为可能性分析：
1. 接收了没回传。（后续必定还会作恶，可通过 Payload 暴露）。
2. 没发送却发送了回传。（属于纯垃圾消息）。
3. 发送了没回传。（虽找不到恶意发送节点，但接收方依然会回传真实内容）。
4. 发送了但是nonce不一样，导致两条单回传。
**处理逻辑：**
*   **回传签名解不开：** 对应情况2（纯垃圾消息）。该消息既未对特定方完成注入、也非针对具体节点的栽赃，按威胁模型原则不予追究，**直接抛弃、不通报任何节点**（同时杜绝恶意节点借单回传对可信名单发起广播栽赃洪流）。
*   **回传签名解得开：**
    *   **若回传签名 ≠ 可信名单**：
    发送了没回传，或者是情况2。必然是可信名单中的某节点为恶意节点，但是找不到具体是谁,一起通报。
    *   **若回传签名 = 可信名单**：
        *   **若后续 Session 中继续出现消息**：判定为“接收了但未回传”。
            * 若出现一条消息能验证身份且身份和当前身份不一致，则说明这条消息不是当前身份发的，那么必然是当前回传消息的Payload 中的 `target_did` 为恶意节点。
            * 若未能出现这类消息，此时消息都是恶意节点发的，不予记录。
        *   **若后续 Session 中未再出现消息**：“未发送却发了回传”或者“接收消息但是没有回传”，但是对session没有影响，直接抛弃此消息,不予记录。
